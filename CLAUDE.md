# elephentity-codegen-wpgraphql

The WPGraphQL builder for [Elephentity](https://github.com/hsimah-services/elephentity): the
IR in on stdin, a compiled GraphQL manifest and its conformance verifier out on stdout.

Read [README.md](README.md), then `PROTOCOL.md` in elephentity-codegen — that is the
contract this implements, and this file assumes it.

## Working in this repository

There is no local PHP. Everything runs in a container:

```bash
./tools/php composer ci          # style, static analysis, tests
./tools/php composer style:fix
./tools/php vendor/bin/phpunit --filter GoldenTest
```

`composer ci` must pass before committing. PHPStan runs at **level max** and there are
no baseline exclusions — the whole claim is that generated code is provably typed, so
an exception here undermines the product.

## What this builder is

Split out of `elephentity`'s `packages/wpgraphql`, which now holds only the runtime
half: the type registrar, the resolvers, the verifier itself. Everything here is
build-time — compiling the spec into the GraphQL manifest the runtime registers at
boot, and into `verify.php`, which names the verifier `eleph check` loads.

It also answers `describe` for the `wpgraphql` integration: `src/Integration/WpGraphQL.php`
is the whole of what keys `integrations: { wpgraphql: … } }` accepts, and it lives here
because the same program that validates those keys also compiles what they configure.

## Depends on nothing of Elephentity's

| Was | Is now | Why |
|---|---|---|
| `Eleph\Schema\Ir\*` | `src/Ir/*`, a copy | a builder that requires the compiler is not pluggable |
| `Eleph\Schema\Integration\IntegrationDefinition`, `Wire\IntegrationCodec` | `src/Integration`, `src/Wire`, own copies | this builder both declares and validates against the same integration |
| `Eleph\WPGraphQL\Manifest\*`, `Verification\WPGraphQLVerifier` | `src/Manifest/*`, own copies | the manifest shapes this builder computes with have to be the same *shape* as the runtime's without being the same *class* |
| `Eleph\Schema\Wire\BuilderEnvelope` | `src/Protocol/BuilderEnvelope.php`, this side only | two implementations of one format is what makes it a protocol |

**`src/Runtime.php`** names the *actual* runtime classes (`Eleph\WPGraphQL\Manifest\Manifest`
and so on) the exported manifest and verifier refer to. Most of them are written bare
into the generated file, relying on it declaring the same namespace they live in at
runtime (`ManifestExporter`); `VerifierExporter` crosses namespaces and interpolates
the one it needs as a string, because it cannot import it — this repository has no
dependency on `elephentity/wpgraphql` at all. If one of those classes is renamed there,
nothing here fails — the exported file still names the old class, and a project that
installed the new runtime fails to load its manifest or verifier at boot. Regenerating
`examples/clog` in `elephentity` is what catches it.

The copies are held in step by the version gate, not a shared classpath.

## Conventions that are load bearing

- **A project that speaks no GraphQL gets no files, `verify.php` included** — see the
  condition in `bin/eleph-gen-wpgraphql`. Finding a manifest with nothing beside it to
  check would be worse than not configuring the target at all.
- **The verifier reads its own manifest off the tree**, not one rebuilt in memory —
  `VerifierExporter`'s whole point is comparing two generated artefacts, which is the
  bug class unique to `eleph check` (elephentity#58).
